# BWU full-faithful integration — design + incremental plan

Routing rqs_lib's receive-path WiFi bandwidth upgrade through nearby-rs's `BwuActor`,
flag-gated behind **`QS_BWU_ACTOR`** (unset = today's proven inline path, zero regression).
beamish/rqs_lib is the BWU **INITIATOR** (offers `UPGRADE_PATH_AVAILABLE` + binds the TCP
listener; the phone dials + is the responder). Derived from the 2026-06-20 mapping workflow.

## Already done (verified, uncommitted)
- **Step A** — `core_lib/src/hdl/ukey_session.rs`: `UkeySession` (Arc, 4 UKEY2 keys, `AtomicI32`
  server/client seq) impls `nearby_rs::bwu::Cipher`; receive path delegates to it; same instance
  survives `set_socket` → seq continuous across the swap. 7 unit tests.
- **Step B.1** — nearby-rs `WifiLanBwuHandler::with_endpoint(sink, bind_ip, advertise_ip)` (no more
  `127.0.0.1`-only). `new` stays loopback. Test added; fmt/clippy/suite green.

## How the two sides actually work (the load-bearing facts)
- **rqs_lib read path** = `handle()` (inbound.rs:240, select! receiver + 4B-BE len read) → `_handle`
  (304, read body) → `process_frame` (322; plaintext `awaiting_introduction` pre-pass + state arms)
  → `decrypt_and_process_secure_message` (677; `UkeySession::decode_payload` + seq pre-incr/`(N vs M)`
  check + `match v1_frame.r#type()` data/BWU demux at 716). Inline BWU arms (911-956) just set
  `upgrade_rejected`/`prior_channel_drained`/`wifi_retry_requested`; the **l2cap.rs driver loop
  (266-409)** polls those flags and runs `offer_wifi_upgrade`/`handover_to_wifi`.
- **nearby-rs BwuActor** NEVER reads a channel itself and NEVER reads data frames. The **consumer**
  reads the old channel and pushes BWU-negotiation frames via `BwuHandle::incoming_frame(pb::OfflineFrame,
  endpoint_id, medium)` (actor.rs:230). The actor reads/writes inline ONLY during the handshake:
  NEW channel = CLIENT_INTRODUCTION read + ACK write (manager.rs:473-486); OLD channel = LAST_WRITE
  write (533), SAFE_TO_CLOSE write (562), DISCONNECTION + 1 drain read + close (582-595); then NEW
  `resume()` + `on_bandwidth_changed(endpoint_id, medium)` (595-597).
- **Construct** with `BwuActor::channel(N)` → `build(rx, handlers, config, local_id)` (NOT `new`) so the
  WIFI_LAN handler's `connection_sink()` exists before the actor. `register_channel` = bare HashMap
  insert (no reader spawned). `run` is `Send` → `tokio::spawn` ok (but see blocking-read risk).

## Required nearby-rs changes
1. **`GetUpgradedChannel` seam** — ✅ **DONE (2026-06-20)**: `BwuCommand::GetUpgradedChannel{ endpoint_id,
   reply: oneshot::Sender<Option<Arc<dyn EndpointChannel>>> }` + `BwuActor::handle` arm (locks ecm,
   `get_channel_for_endpoint` clone, no lock across await) + `BwuHandle::get_upgraded_channel(endpoint_id)`.
   Test in tests/bwu_actor.rs (converged upgrade → getter returns the new channel; None for unknown).
   fmt/clippy-D/full suite green.
2. **Per-handshake read timeout** on the manager's channel reads (manager.rs:450/479/583) — today
   unbounded; rqs_lib bounds drain at 3s (inbound.rs:203). Add a socket read timeout on StreamChannel/
   TcpDuplexStream so a stalled Pixel can't wedge the actor thread.
3. **(optional)** Carry the `Arc<dyn EndpointChannel>` (or the raw `TcpStream`) in the completion signal so
   rqs_lib can `set_socket(Transport::Tcp(tcp))` and keep its proven async `handle()` reader (preferred
   first-cut handoff) instead of adopting a blocking read thread.
4. **`enable_encryption` on the `EndpointChannel` trait** — ✅ **DONE (2026-06-20)**: the trait now has
   `fn enable_encryption(&self, cipher: Arc<dyn Cipher>)` (StreamChannel forwards to its inherent impl;
   FakeEndpointChannel no-ops). Previously the trait only had `disable_encryption`, so a consumer holding the
   swapped `Arc<dyn EndpointChannel>` from `get_upgraded_channel` could NOT install its UKEY2 cipher — the new
   channel is handed back plaintext (`replace_channel_for_endpoint` ignores `enable_encryption`). This seam is
   what lets the StreamChannel-adoption handoff continue an *encrypted, sequence-continuous* transfer on the
   new medium. Pinned by `tests/stream_channel.rs::enable_encryption_works_through_the_trait_object`.

## Hazards (must address)
- **Two writers on the OLD channel**: actor writes LAST_WRITE/SAFE_TO_CLOSE via `StreamChannel::write`
  while rqs_lib may `encrypt_and_send`/`send_frame` the same socket. → Under `QS_BWU_ACTOR`, route ALL
  registered-channel writes through `EndpointChannel::write` so the single `writer_lock` is authoritative.
- **Two readers**: actor's CLIENT_INTRODUCTION_ACK read + SAFE_TO_CLOSE drain read can steal frames from
  rqs_lib's loop. → rqs_lib is sole reader of OLD (feeds BWU via incoming_frame); actor reads only NEW
  during handshake; rqs_lib starts reading NEW only after `is_upgrade_ongoing` flips false. (Interior
  mutability — borrow checker won't catch it; ownership discipline only.)
- **10s prior-channel stall**: the actor's SAFE_TO_CLOSE path does NOT emit the 25× plaintext KEEP_ALIVE
  nudge (l2cap.rs:209-235) that un-parks the Pixel's parked L2CAP read. → keep rqs_lib's `t_out` nudge
  keyed off the actor's completion, or add a post-close hook to the handler.
- **Seq double-advance**: `UkeySession::decode` (Cipher) advances+enforces client_seq, but inline
  `decrypt_and_process_secure_message` also advances via `get_client_seq_inc`. Under the actor path the
  StreamChannel/Cipher must be the SINGLE seq authority; the inline manual seq advance must be skipped (or
  the channel must use `decode_payload` (no advance) + keep the manual check). Decide per step 1/2.
- **`Medium` of the L2CAP StreamChannel** must report `Medium::Ble` so WIFI_LAN is a valid upgrade target
  (`initiate_bwu` precondition `proposed != channel_medium`, manager.rs:230).
